SECTION 1 — THE PROBLEM
════════════════════════════════════════════════════════════════════════════════

THE CONTEXT
-----------
537 million adults worldwide live with diabetes. A further 240 million are
estimated to be pre-diabetic and unaware. For the newly diagnosed — often still
processing the emotional shock of a chronic condition diagnosis — the gap between
leaving the doctor's office and feeling genuinely informed is enormous.

The traditional pathway looks like this:
  - Patient is diagnosed
  - Receives a leaflet or is pointed to a website
  - Waits weeks for a diabetes education appointment
  - Turns to Google, Reddit, or YouTube, where quality is wildly inconsistent
  - Asks questions they were too embarrassed to ask their GP
  - Forms misconceptions that compound over years

THE CORE INSIGHT
----------------
There are two very different user needs that existing tools fail to separate:

  1. NEWLY DIAGNOSED — emotional, scared, overwhelmed, needs clarity and
     reassurance, not medical density. "Will I have to inject forever?"

  2. LIFELONG LEARNERS / CAREGIVERS — curious, informed, want depth and
     evidence. "What is the pathophysiology of insulin resistance?"

Most diabetes websites and chatbots treat these as the same user. They are not.

THE OPPORTUNITY
---------------
A conversational AI that:
  a) Retrieves answers from trusted, curated medical literature  
  b) Adapts its voice and depth to the user's context
  c) Always shows its sources (radical transparency)
  d) Remembers the conversation
  e) Knows who the user is (age, gender) to personalise relevantly
  f) Streams answers in real time so users don't stare at a blank screen

SECTION 2 — THE PRODUCT
════════════════════════════════════════════════════════════════════════════════

PRODUCT NAME: DiaWise
TAGLINE: Diabetes answers, grounded in evidence.

CORE VALUE PROPOSITION
----------------------
DiaWise gives anyone affected by diabetes clear, source-backed answers drawn
from trusted medical literature — available 24/7, no appointments, no sign-up,
personalised to the individual asking.

TARGET USERS
------------
  PRIMARY:    Newly diagnosed type 2 diabetics (ages 35-65)
  SECONDARY:  Caregivers and family members of diabetic patients
  TERTIARY:   Medically curious adults, nursing/medical students, GPs wanting
              a quick second reference

USER GOALS
----------
  - Understand what their diagnosis means in plain language
  - Know what questions to ask their healthcare team
  - Verify claims they've read online
  - Learn at their own pace, on their own time

NON-GOALS (deliberate scope exclusions)
---------------------------------------
  - Personal diagnosis or treatment recommendation
  - Prescription drug interaction checker
  - Real-time blood glucose monitoring integration
  - User account system or cloud data storage
  - Coverage beyond diabetes and directly associated conditions

SECTION 3 — TECHNICAL ARCHITECTURE
════════════════════════════════════════════════════════════════════════════════

STACK OVERVIEW
--------------
  Backend    : Python 3.11 / Flask 3.0
  LLM        : OpenAI GPT-4.1-mini (temperature 0.4, max_tokens 1500)
  RAG layer  : LangChain — retrieve-then-synthesise pipeline
  Vector DB  : Pinecone (index: "diabetesbot", k=4 similarity retrieval)
  Embeddings : HuggingFace sentence-transformers/all-MiniLM-L6-v2 (384-dim)
  Memory     : LangGraph StateGraph + MemorySaver (conversational fallback)
  Caching    : LangChain InMemoryCache (avoids duplicate LLM calls)
  Frontend   : Vanilla HTML5 / CSS3 / JavaScript (ES2020, no framework)
  Deployment : Docker + Gunicorn, PORT configurable via environment variable

KNOWLEDGE BASE
--------------
  Documents are pre-chunked (500 tokens, 20-token overlap), embedded, and
  stored in Pinecone. Retrieval returns the top-4 most semantically similar
  passages to the user's question. Source metadata (document name, page number)
  is preserved through to the UI.

RAG PIPELINE (per request)
--------------------------
  1. User submits question + mode + profile
  2. Emergency keyword scan (13 crisis terms) — fast-path bypass if matched
  3. Profile context prepended: [Patient context: Name, Age, Gender]
  4. Mode flag prepended: [Mode: learning | newly_diagnosed]
  5. Pinecone retriever fetches top-4 relevant passages
  6. LLM streams response token-by-token against context + system prompt
  7. Parser strips FOLLOWUPS / SOURCES structured blocks from raw output
  8. Metadata enrichment fills source list from Pinecone doc metadata if
     LLM did not emit them
  9. Final SSE event delivers complete metadata to client

STREAMING ARCHITECTURE
----------------------
  The /ask endpoint returns text/event-stream (Server-Sent Events).
  Every approach in the LLM chain (main RAG path, LangGraph fallback,
  emergency fast-path, error state) emits:
    - Zero or more  data: {"token": "..."}   events during generation
    - Exactly one   data: {"done": true, "answer": ..., ...}  closing event

  The frontend reads the stream via the Fetch ReadableStream API, rendering
  tokens into a live text node. On the "done" event the raw text is swapped
  for markdown-rendered HTML. A blinking cursor CSS animation is shown during
  streaming to communicate progress without a spinner.

  Response headers:
    Cache-Control: no-cache
    X-Accel-Buffering: no   (disables nginx proxy buffering)
    Connection: keep-alive

FALLBACK CHAIN
--------------
  PRIMARY:  LangChain RAG chain (retriever + GPT-4.1-mini)
      |
      v  on exception
  SECONDARY: LangGraph conversational memory graph
      |
      v  on exception
  TERTIARY: Static error message with safety note

SAFETY ARCHITECTURE
-------------------
  Layer 1 — Emergency keyword scan (pre-LLM, <1ms):
    13 keywords including: unconscious, seizure, DKA, ketoacidosis,
    loss of consciousness, not breathing. Returns 999/911 directive
    immediately without calling the LLM.

  Layer 2 — System prompt constraints:
    Scope-limited: "I'm only able to help with diabetes and related
    health topics." for off-topic queries.
    No personal diagnosis. No treatment prescriptions.
    Every medication/symptom answer includes a consult recommendation.
    "SOURCES: - General medical knowledge" if no retrieved context used.

  Layer 3 — Frontend disclaimer:
    Every response carries a static safety note appropriate to mode.
    Permanent footer: "Educational use only. Not medical advice."

  Layer 4 — No hallucinated citations:
    Structurally prevented — sources are either parsed from LLM structured
    output OR extracted from Pinecone document metadata. If neither exists,
    "Diabetes Reference Document" or "General medical knowledge" is shown.
    The LLM cannot invent a citation without the parser seeing it.

SECTION 4 — PRODUCT FEATURES (SHIPPED)
════════════════════════════════════════════════════════════════════════════════

FEATURE 1: REAL-TIME STREAMING ANSWERS
---------------------------------------
Problem solved: Users abandoned the UI when staring at a blank screen for
3-5 seconds. The perception of latency was worse than the actual latency.

Solution: SSE streaming from the first LLM token. A blinking cursor signals
activity instantly. The answer builds visibly, word by word, in the same way
reading feels natural — the user comprehends as the text arrives.

Implementation:
  - Flask Response(stream_with_context(generate()), mimetype='text/event-stream')
  - Frontend: fetch() + ReadableStream reader + TextDecoder
  - Live text node updated per token (no innerHTML writes during stream)
  - Markdown rendered only on stream completion (no mid-stream re-render jank)

PM rationale: Streaming is table stakes for any LLM product in 2025+. This
was the single change with the highest perceived performance lift.

---

FEATURE 2: TWO-MODE ADAPTIVE RESPONSES
----------------------------------------
Problem solved: A one-size-fits-all tone is wrong for this audience. A
terrified newly-diagnosed 55-year-old and a curious medical student have
fundamentally different emotional and informational needs.

Solution: Mode toggle in the app header.
  - LEARNING MODE: Dense, educational, clinical detail, all terminology
    explained, numbered steps for processes, rich citations.
  - NEWLY DIAGNOSED MODE: Warmer, simpler, reassuring. Shorter sentences.
    Human-first framing. No jargon without immediate plain-language follow-up.

The mode is injected into every LLM call: [Mode: newly_diagnosed] prefix in
the augmented question controls tone at the system-prompt level.

PM rationale: Mode is a proxy for emotional state, not just knowledge level.
This design decision is what separates DiaWise from a generic health AI.

---

FEATURE 3: ONBOARDING PROFILE CAPTURE
---------------------------------------
Problem solved: Anonymous queries produce generic answers. "What should I eat?"
means something very different for a 22-year-old woman vs a 68-year-old man.

Solution: First-visit onboarding modal. Captures:
  - First name (required — used to personalise responses throughout session)
  - Age (optional — enables age-appropriate framing)
  - Gender (optional — enables gender-specific medical considerations)

Stored in: localStorage (key: diawise_profile). Never sent to a server.
Used in: Every API call as a [Patient context: ...] prefix. System prompt
instructs the LLM to address the user by first name occasionally, tailor
age-relevant advice, and acknowledge gender-specific considerations without
making assumptions.

PM rationale: Personalisation is the clearest signal of product maturity.
Zero-server-cost personalisation via localStorage satisfies privacy concerns
while delivering a meaningfully better experience.

---

FEATURE 4: EVIDENCE PANEL (SOURCE TRANSPARENCY)
-------------------------------------------------
Problem solved: Health AI faces a fundamental trust problem. Users cannot
evaluate AI answers without seeing their basis.

Solution: Sliding evidence panel alongside every conversation:
  - Shows each source document and page number
  - Color-coded: emerald badge for "From knowledge base" (RAG retrieved),
    amber badge for "General knowledge" (no specific document retrieved)
  - Safety note mode-appropriate in every panel entry
  - Accessible (aria-label, aria-hidden, role attributes throughout)

PM rationale: Radical source transparency is a design principle, not a
feature. For health AI it is an ethical requirement. The evidence panel
converts what would be an opaque answer machine into a verifiable reference
tool — closer to a librarian than a chatbot.

---

FEATURE 5: PERSISTENT CHAT HISTORY (NO ACCOUNT)
-------------------------------------------------
Problem solved: Health questions are rarely one-shot. Users build understanding
over time, return with follow-up questions, and want context continuity.

Solution: Full chat history stored in localStorage (key: diawise_history,
capped at 100 entries). Conversations survive browser restarts. Clearing
history requires explicit confirmation. No signup, no server, no data at risk.

PM rationale: Removing sign-up friction was a deliberate acquisition decision.
The target user (newly diagnosed, older cohort) has high drop-off at
registration gates. localStorage history achieves 90% of the benefit at 0%
of the privacy cost.

---

FEATURE 6: SMART FOLLOW-UP CHIP ENGINE
----------------------------------------
Problem solved: Most users don't know what they don't know. After receiving an
answer, they reach a "now what?" dead end. Session depth is 1-2 messages.

Solution: The system prompt instructs the LLM to always output a FOLLOWUPS:
block with 2-3 short follow-up questions generated from the answer context.
These are parsed out, stored in the response payload, and rendered as
clickable chips below the conversation. One tap loads the question and submits.

PM rationale: Follow-up chips increase session depth and learning engagement.
They are AI-generated for the specific answer, not generic "people also asked"
patterns — making them contextually useful rather than filler.

---

FEATURE 7: EMERGENCY FAST-PATH
--------------------------------
Problem solved: A small but critical user segment may describe acute symptoms
in what they perceive as an informational context (DKA, severe hypoglycemia,
loss of consciousness). Any LLM processing delay for these queries is
unacceptable — and a wrong answer is a liability.

Solution: Synchronous pre-LLM keyword scan against 13 crisis terms. Match
returns an immediate 999/911 directive within <1ms, bypassing the LLM entirely.
The entire response path still uses SSE, so the client handles it identically.

PM rationale: Safety-critical paths must be deterministic and fast. No LLM
should be in the loop for a potential life-or-death response. This is the
only non-negotiable feature — it ships before anything else, always.

---

FEATURE 8: LANDING PAGE — TRUST-FIRST INFORMATION ARCHITECTURE
----------------------------------------------------------------
Problem solved: An AI health tool has zero trust by default. Users need to
understand the product's approach before typing their first health question.

Solution: Full marketing/trust landing page at / with:
  - Hero: Value prop + demo preview card showing a real answer w/ source
  - Stats bar: 537M affected, 50% undiagnosed, 24/7 availability, RAG
  - Feature grid: 6 cards explaining differentiated capabilities
  - How it works: 4-step RAG pipeline (plain language)
  - Trust section: Source transparency, no server storage, emergency
    escalation, educational-only commitment — with badge evidence
  - CTA section with direct path to /ask

PM rationale: For a health AI, "what makes this safe and credible" must be
answered before "what does it do". Landing page IA order reflects this.

SECTION 5 — DESIGN SYSTEM

DESIGN LANGUAGE
---------------
DiaWise uses a "Medical-tech meets human warmth" visual language. The goal is
to feel as precise and credible as a clinical tool while remaining as warm and
approachable as a conversation.

Reference aesthetic: Linear.app (precision + density) crossed with
Perplexity AI (research transparency) crossed with Levels Health (medical
consumer product). Built from scratch in vanilla CSS.

COLOR SYSTEM
------------
  Core palette — deep space medical:
    --bg-void:   #03060f   (page background — near-black)
    --bg-deep:   #060c1a
    --bg-base:   #09112a
    --bg-raised: #0e1a35   (card surfaces)
    --bg-glass:  rgba(14,26,53,0.7) (glassmorphism panels)

  Brand spectrum (deliberate choice: NO violets or pinks in text):
    --cyan:      #00e5ff   (primary action + brand identity)
    --emerald:   #10b981   (success / retrieved sources / trust)
    --amber:     #f59e0b   (caution / general knowledge / warnings)
    --red:       #ef4444   (emergency / destructive actions)

  Text hierarchy:
    --text-1: #f0f6ff   (primary)
    --text-2: #94a3b8   (secondary)
    --text-3: #4e6080   (hint / disabled)

TYPOGRAPHY
----------
  Display: Sora (600, 700, 800 weights) — geometric, precise, distinctive
  Body:    Inter (400, 500, 600 weights) — neutral, highly legible at small sizes
  Mono:    JetBrains Mono — code and inline terms

ANIMATION PRINCIPLES
--------------------
  All motion serves a communicative purpose:
    - Spinning conic gradient rings on logo: brand identity, aliveness
    - Mesh background + floating orb: depth, not distraction
    - Particle drift (hero): organic motion, ultra-subtle opacity
    - msgIn spring keyframe: messages feel physical, not digital
    - Streaming cursor blink: status communication
    - Typing dot sequence: feedback during loading
    - Send button pulse on loading: replaces a spinner
    - Card hover lift + glow: affordance without skeuomorphism

ACCESSIBILITY
-------------
  - Semantic HTML throughout (nav, main, header, aside, form, role attributes)
  - All interactive elements have aria-label, aria-pressed, aria-expanded
  - Focus-visible ring on all interactive elements (2px cyan, 3px offset)
  - Color alone never used to convey meaning (labels accompany color coding)
  - Screen reader text preserved across evidence panel state changes

RESPONSIVE BREAKPOINTS
----------------------
  900px: Nav links collapse, evidence panel switches to slide-over, how-it-works
         track becomes vertical stacked with row steps
  600px: Hero preview card hidden (mobile bandwidth), single-column feature
         grid, mode toggle hidden (space constraint), input bar simplified

SECTION 6 — PRODUCT DECISIONS LOG
════════════════════════════════════════════════════════════════════════════════

Each decision below was a deliberate PM-level trade-off.

DECISION 1: No user authentication
  Option considered: Email/password or OAuth signup
  Chosen approach: Anonymous with localStorage persistence
  Rationale: Target user skews older, less digitally confident. Sign-up
  friction would destroy top-of-funnel conversion. Health data in a database
  creates a liability surface. localStorage gives 90% of the persistence
  benefit with 0% of the privacy and compliance cost.
  Trade-off accepted: History is device-bound. Users lose history if they
  clear browser data or switch devices.

DECISION 2: Two modes instead of a slider / free-text persona
  Option considered: Continuous tone slider, or "tell us about yourself" free text
  Chosen approach: Binary toggle (Learning / Newly Diagnosed)
  Rationale: Binary reduces cognitive load. Users cannot be expected to
  calibrate a slider for something as abstract as "tone". The two modal
  extremes cover 80% of real use cases. Mode can be changed per-question.
  Trade-off accepted: Loses nuance for edge cases (e.g. a nurse who is
  also newly diagnosed with her own diabetes).

DECISION 3: Streaming over batch response
  Option considered: Show a spinner, return full answer in one payload
  Chosen approach: SSE token-by-token streaming
  Rationale: Health questions are emotional. A blank screen + spinner for
  4 seconds creates anxiety. Streaming text builds comprehension as it is
  generated. Perceived latency drops dramatically. The technical cost is low
  (Flask supports streaming natively). The UX gain is transformative.
  Trade-off accepted: Broken network connections mid-stream result in a
  partial bubble. Fallback catches stream errors and shows an error message.

DECISION 4: Evidence panel as a slide-over, not always-visible
  Option considered: Fixed two-column layout with sources always visible
  Chosen approach: Triggered slide-in sidebar
  Rationale: On the most common screen (laptop, 1280px wide), the chat
  area plus a fixed source column would feel crowded. The evidence panel
  is secondary information — it should be available on demand, not competing
  for primary attention. Toggle auto-opens on each response.
  Trade-off accepted: First-time users may not discover the toggle. Mitigated
  by "Sources" button label (not just an icon) in the app header.

DECISION 5: Structured LLM output (FOLLOWUPS / SOURCES blocks)
  Option considered: Post-call to a second LLM endpoint for follow-ups
  Option considered: Hard-coded follow-up pattern matching
  Chosen approach: Single LLM call with structured output blocks in system prompt
  Rationale: A second LLM call doubles latency and cost. Hard-coded follow-ups
  are generic and low quality. Instructing the LLM to output structured blocks
  in a single pass gives contextual, high-quality follow-ups at zero additional
  latency or API cost. Parser strips FOLLOWUPS and SOURCES before the visible
  answer is rendered.
  Trade-off accepted: The LLM occasionally fails to produce the structured
  blocks. The source extraction fallback (Pinecone doc metadata) covers the
  SOURCES case. Missing follow-ups degrade gracefully (chip bar simply empty).

DECISION 6: Flat file deployment (no Docker Compose or external DB)
  Option considered: Postgres + Redis + separate worker + docker-compose
  Chosen approach: Single Flask process + Pinecone (external managed vector DB)
  Rationale: For a portfolio prototype, the operational complexity of a full
  Docker Compose stack is noise. Pinecone is already managed infrastructure.
  Single-process Flask + Gunicorn is deployable to Render, Railway, or Fly.io
  in under 10 minutes. State is either in Pinecone or in the client.
  Trade-off accepted: Not horizontally scalable without LangGraph session
  affinity — production would require persistent session storage (Redis).

DECISION 7: HuggingFace embeddings over OpenAI embeddings
  Option considered: text-embedding-3-small (OpenAI)
  Chosen approach: all-MiniLM-L6-v2 (HuggingFace, 384-dim, local inference)
  Rationale: MiniLM runs locally — zero embedding API cost and zero latency
  added for the embedding call. For a static, pre-indexed knowledge base, the
  quality difference vs OpenAI embeddings is negligible. The knowledge base
  does not change at inference time.
  Trade-off accepted: If the knowledge base were dynamic (user-uploaded docs),
  OpenAI embeddings would be worth the cost for consistency with the LLM's
  internal representation.

SECTION 8 — METRICS FRAMEWORK
════════════════════════════════════════════════════════════════════════════════

Note: DiaWise is currently a portfolio prototype. The following defines
the metrics framework that would govern a production product.

NORTH STAR METRIC
-----------------
  "Questions answered with a cited source"
  Rationale: Captures product value (question answered) + trust signal
  (source provided) in a single metric. Avoids optimising for raw volume
  (which could include low-quality exchanges).

ACQUISITION
-----------
  - Landing page to /ask conversion rate (target: >35%)
  - Onboarding completion rate (target: >80%)
  - Returning visitor rate after 7 days (target: >25%)

ENGAGEMENT
----------
  - Questions per session (baseline: 1-2, target: >4 via follow-up chips)
  - Follow-up chip click rate (measures chip engine value)
  - Mode toggle usage rate (measures mode feature adoption)
  - Evidence panel open rate (measures source transparency value)
  - Session depth vs mode (learning vs newly diagnosed — are modes serving
    their intended user types differently?)

QUALITY
-------
  - Source retrieval rate (% of responses with "From knowledge base" vs
    "General knowledge") — target: >70% retrieved
  - Emergency fast-path trigger rate (monitor for abuse, also validate
    keywords are not over-triggering)
  - User-initiated clears (proxy for dissatisfaction)

SAFETY
------
  - Emergency fast-path P99 response time (must be <50ms)
  - Error rate on /ask endpoint
  - Fallback trigger rate (indicates primary chain health)

SECTION 10 — LESSONS LEARNED
════════════════════════════════════════════════════════════════════════════════

1. THE MOST IMPACTFUL ENGINEERING CHANGE WAS ALSO THE MOST EMBARRASSING
   The RAG chain was instantiated but never called. Every response was being
   generated from pure LLM knowledge with no retrieval — the entire technical
   differentiator of the product was dormant. Fixing this one line transformed
   response quality. Lesson: integration tests for the critical path are not
   optional.

2. SYSTEM PROMPT DESIGN IS PRODUCT DESIGN
   The original prompt had three contradictory strategies. The LLM was being
   asked to choose between "only use context", "acknowledge if no context", and
   "start with a ritual first-message question" simultaneously. The result was
   an unpredictable, inconsistent product voice. A single, clear strategy with
   explicit fallback ordering is the correct approach.

3. PERCEIVED PERFORMANCE > ACTUAL PERFORMANCE
   Streaming does not make the LLM faster. Total time to complete answer is
   identical. But the user experience is night-and-day better. In a health
   context this matters even more — users staring at a blank screen while
   worrying about a health concern is an active harm.

4. TRUST IS AN ARCHITECTURAL DECISION
   Source transparency is not a nice-to-have UI feature — it is the reason a
   health AI product earns the right to be used at all. The evidence panel,
   the source metadata extraction, the "retrieved vs general" color coding,
   the disclaimer on every response — these are not polish. They are the
   product's ethical backbone. They were designed in from the start.

5. PERSONALISATION CHANGES THE EMOTIONAL EXPERIENCE
   Adding "Hi Alex" to the welcome screen and "[Patient context: Age: 54]" to
   the LLM prompt changes something intangible. The product feels like it is
   talking to you, not at you. This is the difference between a tool and a
   service. The cost was two localStorage reads and a string prefix.

6. VANILLA STACK IS A PORTFOLIO ASSET
   The entire frontend is raw HTML, CSS, and JavaScript. No React, no Tailwind,
   no bundler. This demonstrates that the design quality, animations, and
   interaction patterns came from understanding CSS and JS deeply — not from
   a framework doing the work. Every hiring manager who looks at the source
   will see this immediately.
